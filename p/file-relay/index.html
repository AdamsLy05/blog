在服务器上开个文件中转站

想在自己几台设备之间倒文件，最后发现最麻烦的从来不是传输本身。

2026 年 11 月 03 日 阅读时长: 2 分钟
目录

需求很朴素：手机和电脑之间传文件。

听起来是件早就被解决的事。但真到自己身上，会发现问题不在"能不能传"，在"要不要为这件事多开一个 App、多登一个账号、多记一套密码"。

先看看现成的

一条条试：

  • 微信/QQ 传文件：能传，但经过谁、存多久、压缩不压缩，你说了不算。而且手机上想传到电脑，得先找到一个愿意接收的会话
  • 网盘：要登录、要同步、要大。
  • 同一 WiFi 下的 LocalSend：体验最好，点对点直连，不过服务器。但只在同一个网络里有用
  • croc：命令行一行搞定，端到端加密，跨网络也行。适合偶尔传一个文件

这些都不错。问题是我手边正好有一台 7×24 开着的服务器，不用它反而有点浪费。

所以搭了个中转

dufs，一个 2MB 的单文件 HTTP 服务。特性刚好：

  • 拖拽上传、点一下就下载
  • 支持删、支持把整个文件夹打包下载
  • 有 Basic Auth
  • 可以只监听 127.0.0.1

最后一条是关键。只监听本机，公网就碰不到它，要用的时候从自己电脑开一条 SSH 隧道过去：

ssh -N -L 5200:127.0.0.1:5200 root@服务器

然后浏览器开 127.0.0.1:5200，就是个能拖文件的网页。

用完把隧道一关，服务就当不存在。

但它不是最优解

文件要先经过一台不属于我的机器——虽然是自己的服务器，但它在云上，中间多了一道不该有的环节。

按场景分，其实应该是这样：

场景用什么
手机 ↔ 电脑，同一个 WiFiLocalSend，直连，最快
跨网络传一个文件croc，一行命令
想要"随手一扔"的固定入口服务器中转
长期想省心Tailscale 组网，之后所有服务都不用开隧道

最后那条才是真正的解。它不是"传文件工具"，是把几台设备变成一个局域网——之后不管是文件、还是网页、还是数据库，都不用再考虑"怎么连过去"。

我用中转，是因为它今天就能用，不需要在三个设备上装客户端、登同一个账号。

这是图省事，不是最优解。

一个容易忽略的细节

服务跑起来之后，我第一件事不是试着上传，是测试没密码能不能进。

无密码访问 401

401 才对。这种"默认应该是拒绝"的东西，最好在放文件之前就验一遍，而不是等哪天发现目录里多了看不懂的文件。

2026-11-03，隧道一关，它就不存在。
