不知道，是一种状态

相册索引和 AI 提示词，两个不相干的东西，栽在同一个错误上：把"没读到"当成了"没有"。

2026 年 11 月 02 日 阅读时长: 4 分钟
目录

有两件事看起来毫无关系：一个是手机相册的索引同步，一个是让模型拆解视频创意。

它们栽在同一个错误上——把"不知道"当成了"没有"。

一、相册：三种事实，我写成了两种状态

加相册功能时，我写了个很自然的逻辑：

索引里有、相册里没有 → 说明用户删了 → 从索引里删掉。

跑起来才发现问题。手机刚开机、系统还在做媒体扫描、用户只给了一半权限——这些时候扫描会读到「零张照片」。按上面的逻辑，整个索引会被判成"已删除"，一次性清空。

用户看到的是回忆全没了。

真实情况有三种：

事实我当时的表达
照片在在列表里
照片确实不在了不在列表里
读不到（失败、没权限、正在扫描）也不在列表里 ❌

第三种被塞进了第二种。代码上就差一个返回值：

// 错的：失败也返回空列表
fun query(): List<Media> =
    runCatching { medias }.getOrDefault(emptyList())

// 对的：失败返回 null，只有真的没有才是空列表
fun query(): List<Media>? =
    try { medias } catch (e: Exception) { null }

改完之后，同步逻辑变成：读取成功就按差异增删，读取返回 null 就什么都不做，保留旧索引。

同一个坑还有两个变种：授权不能用一个布尔值表示（要分成「完整 / 部分 / 无」），以及"暂时看不见"的照片要能恢复，不能删。

二、模型：给它一个说「不知道」的地方

做 UVS 时定了条规矩：它可以问我，但不能替我决定。

第一版很朴素——“请把用户创意整理成 JSON，缺的信息不要编”。结果它编得挺好：用户只写了"拍个视频"，它能生成一份处处合理的 JSON，主体是"人物"、场景是"城市街道"、光线是"自然光"。每一条都说得通，每一条都不是用户说的。

问题不在于它编得差，在于它编得太好，好到看不出是编的。

解法是给"不知道"一个字段，而不是反复叮嘱它别编：

{ "field": "environment.timeOfDay", "reason": "用户没提光线", "level": "B" }

分级是配套的：A 级必须问用户（主体、核心事件、结尾），B 级先给建议但要标出来，C 级可以自动补全、同样要标。

改完才发现，模型不是不愿意诚实，是没有地方可以诚实——不给字段，它只能在"编一个"和"什么都不写"之间选。

三、留了字段还不够

有了 unknowns 之后，新问题来了：它会一边问你三个问题，一边把完整的 JSON、提示词、分镜全放出来。等于没确认就定稿。

根因在我这儿：判断能不能定稿时，我只检查了结构对不对，没检查有没有未确认的 A 级项。

改成：只要 unknowns 里有任何 A 级条目，结果就不算通过，输出区不出现。

另外两个意料之外的坑：

  • 模型对"什么算 A 级"有自己的一套。 它会顺手把「环境地点」也标成 A 级，结果问了一堆我没打算问的。修法是把 A 级写成枚举——具体哪几项，而不是"重要的那几项"。
  • 语言会漂。 前几轮中文，某一次突然冒出英文提问。加两条硬规则才稳住：提问必须简体中文，自由文本（除枚举外）必须简体中文。

输出不合规时，把具体错误回给它，让它只改错、不重写：

你上一次输出的 JSON 有 2 处不符合规范：
1. environment.timeOfDay：期望 night，收到「夜晚」
2. environment.details：期望数组，收到字符串

这比单纯重试有用。重试是碰运气，带错误回去是让它知道错在哪。

它们其实是同一件事

相册那边，null 和空列表是两个值；模型这边，unknowns 和"编一个"是两条路。

共同点是：你的数据来自外部，就必须给"没拿到"留一个位置。 没有这个位置，它只能被挤进"没有"，而一旦被当成"没有"，程序就会去做一些不可逆的事——删索引、定稿、发出去。

区别只在于：想清楚这件事之前，两边的代码看起来都是能跑的。

2026-11-02，两个坑，同一个原因。
