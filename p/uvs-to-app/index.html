把一个网页工具搬进手机

网页版能用，但它得靠一台服务器的常驻服务。所以我把它重写成了安卓 App。

2026 年 11 月 03 日 阅读时长: 3 分钟

UVS Studio 的网页版已经能用了：写一段创意，它拆成结构化需求，再吐提示词和分镜。

问题是它挂在服务器上。哪天那台机器停了，或者我把它删了，这个每天都要用的工具就没了。

所以昨天先写了份计划书，今天把它做成了安卓 App。

先说选型：为什么不套壳

“套壳"就是用 WebView 打开网页，最省事。三条路我摆了张表：

方案工作量关键问题
PWA 加桌面图标几乎为 0服务器一停就废
WebView 套壳小浏览器 CORS 挡住直连 DeepSeek，得靠原生层转发
原生 Kotlin中逻辑要重写一遍（约 600 行 TS）

选了原生。理由不是"原生更高级”，是我不想让工具的核心功能挂在别人能关掉的地方。加上历史记录要能离线翻，套壳那条路两样都做不到。

顺带一个私心：理砚也是 Kotlin + Compose + Room，同一个技术栈，出问题我知道往哪看。

真正的风险不是"做不出来"

写代码这一步，我几乎不担心。逻辑简单——输入文本、调一次接口、展示结果，没有相机、没有传感器、没有后台服务。

真正会出事的是另一件事：做出来和网页版不一样。

提示词是要直接粘到生成平台去的。差一个换行、少一个顿号，效果就可能变。而这种错误特别隐蔽——App 能跑、界面好看、测试全绿，就是你用的时候觉得"怎么没网页版那个味道"。

所以我定的第一个硬要求是 golden 测试：拿五个固定样例，用网页版的实现生成提示词，把字符串存成基准；安卓侧的输出必须一字不差。

golden 对齐 5/5

这条我没打算只信测试报告。我把用例的 JSON 抽出来，重新跑一遍网页版的实现，跟期望值逐字比对——对上了，才算数。

计划书里别的都能商量，这条没得让。

计划书里的天数，全删了

第一版计划书里的排期是：核心链路 3 天、界面 8 天。

写完回头看，这数字明显不对——我开发上一个 App，前后也就一天。

问题出在单位：那是"一个人慢慢敲"的人天。而这次真正的瓶颈不在敲代码，在于反复核对输出有没有走样。人天这个单位在这儿不成立。

所以把天数全删了，只留 M0 到 M6 的顺序、每个阶段的验收，和那张"Web 版文件 → Android 文件"的对照表。

一天，80 个测试

结果：55 个文件、6000 多行，./gradlew test 跑了 80 个用例，debug 和 release 两套都过。

真机上装了，用起来没问题。

代码写完，重点核了三处：

  • Key 有没有硬编码：没有，走 AndroidKeyStore 的 AES-GCM 加密，全项目只有一个类读它
  • 日志会不会漏 Key：一行 Log 都没有
  • 规则有没有漏：R2 到 R7 的报错文本和网页版一字不差——这段文字会原样回灌给模型做修复，差一个字都会让它修歪

定验收比写代码难

回头看，这次真正决定成败的动作只有两个：

  1. 定验收——什么算做完了。这次就是那句"golden 不通过，不许碰界面"
  2. 判断取舍——套壳还是原生、先做什么后做什么

这两个定错了，代码写得再快也是白跑。而定它们花不了多少时间，所以才容易被人跳过。

留下的问题

参考图/首帧还没做。手机上这块其实比网页版顺手——相机现成的，拍一张就是参考，不用来回传文件。
