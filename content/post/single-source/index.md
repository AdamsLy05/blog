UVS Studio 要产出四样东西：结构化 JSON、中文提示词、分镜时间轴、平台适配说明。

一开始我很自然地想：**让模型一次全写了吧**，反正它都能写。

结果第一版就露馅了。

---

## 矛盾是怎么来的

用户要 5 秒。JSON 里 `durationSec: 5`，但提示词里写着"约 10 秒的画面"。分镜表的时间轴是 0–5 秒，提示词却在描述三段镜头。

每一处都不算错，合起来就是错的。

原因很简单：**这是四次独立的生成**。模型不知道 JSON 里写了什么，它只是在扮演"写提示词的人"。上下文再长，也不如一句确定的字段可靠。

---

## 换个分工

我改成：**模型只负责"理解"，不负责"表述"**。

- 模型干一件事：把自然语言变成 JSON（这是它擅长的，也是必须的）
- 其余三样，全部由代码从 JSON 派生

提示词是模板拼出来的：

```
5 秒竖屏（9:16）。
场景：夜晚，下雨，便利店靠窗的柜台。
主体：橘色短毛猫，体态偏胖，趴在玻璃柜台后。
镜头：特写，推轨，缓慢推近。
光线：柔光、侧光、暖调。
分镜顺序：1. 0–2 秒：全景… 2. 2–5 秒：特写…
要求：不要真人；不要出现品牌标识。
```

分镜表就是 `timeline` 数组渲染成表格。适配说明是查表。

---

## 这样做换来了什么

**一、不可能矛盾。** 提示词里的每个数字都来自 JSON，改时长就是改一处，不会漏。

**二、不花钱。** 从 JSON 到提示词零成本，用户点一次不需要等模型。

**三、可预测。** 同一个 JSON 永远生成同一段提示词。模型那边你再怎么调温度，这边都不会变。

代价是**文风僵硬**。模板拼出来的句子是"零件式"的，读起来像一个填好的表格，不像人话。

我认为这个代价值得——**提示词是给机器看的，不是给人看的**。机器不在乎文采，在乎准确。

---

## 那英文版怎么办

英文提示词确实需要翻译，这部分我交给模型，但加了明确约束：

> 不要逐字直译；使用行业通用术语（close-up / dolly-in / soft light）；时长画幅照原样保留；所有硬性要求完整译出。

这一步是有边界的：**只翻译一段已经确定的文本，不让它参与创作**。翻错了可以看出，编错了看不出来。

---

## 一个更普遍的原则

这件事不只适用于视频工具。

任何"一份数据、多种输出"的系统都会遇到同一个问题：**多个出口各自生成，迟早不一致。**

正确的做法是让所有出口都指向同一个源头。中间可以有转换、有翻译、有排版，但不能有第二次"理解"。
