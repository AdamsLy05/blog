我在给 App 加相册功能时，写过一个"想当然"的逻辑，后来花了整晚把它拆掉。

---

## 起点：一个很自然的想法

本地数据库里存着相册的索引。每次进页面重新扫一遍相册，然后：

> 库里有的、相册里没有的 → 说明用户删了 → 从索引里删掉

很合理，对不对？

跑起来才发现是灾难。手机刚开机、系统还在做媒体扫描、或者用户只给了一部分权限的时候，扫描会读到「零张照片」。按上面的逻辑，**整个相册的索引会被判成"已删除"，一次性清空**。

用户看到的是「回忆全没了」。

---

## 根因：用两种状态表达了三种事实

真实世界里的情况有三种：

| 事实 | 我当时的表达 |
|---|---|
| 照片在 | 在列表里 |
| 照片确实不在了 | 不在列表里 |
| **不知道**（读取失败、权限不足、正在扫描） | **也不在列表里** ❌ |

第三种被硬塞进了第二种。代码上就是：

```kotlin
// 错的
fun query(): List<Media> =
    runCatching { medias }        // 失败时返回空列表
        .getOrDefault(emptyList())
```

读取失败和"确实是空的"，返回了同一个值。

---

## 改法：把"不知道"显式建模

```kotlin
// 对的：失败返回 null，只有真的没有才返回空列表
fun query(): List<Media>? =
    try { medias } catch (e: Exception) { null }
```

然后同步逻辑变成：

- 读取成功 → 按差异增删
- **读取返回 `null` → 本次什么都不做**，保留旧索引

一行 `null` 的差别，决定的是"用户数据会不会消失"。

---

## 同一个坑的另外两个变种

**授权判定。** 用户可能只给了视频权限、没给照片权限。如果把这判成"完整授权"，同步时就会把照片索引全删掉。所以授权级别要单独建模成「完整 / 部分 / 无」，而不是一个布尔值。

**"不可见"要能恢复。** 部分授权下，看不见的照片应该标成"暂不可见"，而不是删除——因为用户随时可能把权限给回来。如果直接删了，就要重建整个索引，体验很差。

---

## 一句话结论

**只要你的数据来自外部、并且有缓存，就必须把"读取失败"和"结果为空"当成两个不同的东西。**

这个道理放在网络、文件、系统 API 上都一样。区别只在于：想清楚这件事之前，你的代码看起来是完全可以跑的。
